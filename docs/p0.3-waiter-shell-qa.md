# P0.3 waiter shell QA

The shell lives under `/waiter/tables/layout.tsx`. It owns preparation,
tables polling, availability, READY detection and sound preference. Each
table has a keyed OrderClient instance; no order/cart is stored in the shell.

## Verified with mounted React components

The request recorder in `tests/unit/waiter-shell.test.ts` exercises actual
PosClient, OrderClient and WaiterShellProvider with mocked HTTP responses.

| Step | Requests triggered by navigation |
| --- | --- |
| Initial entry | GET me, snapshot, availability, shift, tables |
| Tables → table 5 | POST orders, GET order detail |
| Table 5 → tables | None |
| Tables → table 12 | POST orders, GET order detail |
| Table 12 → tables | None |
| Reopen table 5 | POST orders, GET order detail |

The three opens together trigger six order requests, zero extra identity,
category or static-menu requests. Polling is separate: tables every 5s,
availability every 15s while an order is open, applicable order status every
4s. Overlapping polls are skipped/deduplicated.

The prepared menu is rendered while the authoritative order response is
held unresolved. Item buttons stay disabled until that response arrives.
Returning to tables needs no network response. These are component/network
dependency observations, not measurements of real-device latency or Next.js
route bundle/RSC transfer time.

## Development timing

Development builds record User Timing entries without console logging:

- `waiter:preparation`: identity through complete prepared data.
- `waiter:menu-visible`: table click through prepared menu mount.
- `waiter:order-open`: authoritative order POST and detail GET.
- `waiter:tables-visible`: back click through tables mount.

After the route sequence, inspect:

```js
console.table(performance.getEntriesByType('measure')
  .filter(entry => entry.name.startsWith('waiter:'))
  .map(({ name, duration }) => ({ name, milliseconds: duration.toFixed(1) })));
```

Use Network with Preserve log to distinguish API requests from framework
route navigation. Initial development route compilation can add latency;
collect warmed-route timings separately. There is no production logging.

## Manual QA

A. Login waiter → preparation appears once → "Smena je spremna".

B. Open Table 5 → menu visible → back.

C. Tables appear immediately → no preparation screen.

D. Open Table 12 → no menu-loading wait. The order may still be opening;
menu items cannot mutate an order until its authoritative response arrives.

E. Back → reopen Table 5 → no static menu refetch.

F. While inside Table 5, make another table/order READY → waiter notification
must still work. Only the responsible waiter's tables should notify. Check
sound after a user gesture, muted preference, and no false first-load alert.

Also check a rapid quantity change followed by Submit, remove followed by
Submit, failed mutation followed by retry, and logout/quick lock followed by
another employee login and browser Back. No previous employee data should
reappear. A restored back/forward-cache document is reloaded.

No real browser/backend timings were collected in this session: no local
app/CDP endpoint or configured TEST_DATABASE_URL was available. Automated
database integration tests were not run against Development/Production.
Real-device sound policy and route latency remain QA checks.
