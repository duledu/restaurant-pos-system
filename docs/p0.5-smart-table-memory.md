## Behavior and authoritative inputs

The compact Brzo dodaj row offers at most eight modifier-specific selections.
Chips have 48px minimum height and horizontal overflow, keeping the menu close.
Each chip is an explicit +1 action. Existing draft quantity controls remain.
Stars identify shift/session favorites; table-specific entries come first.
All calculations use the current table's shell draft/order and prepared menu;
there are no suggestion requests or menu refetches.

`getOrder` already returns full item fields, ordered by createdAt. `submitOrder`
assigns the same `submittedAt` to all DRAFT items in one transaction. The client
type now exposes this existing field; the API and database are unchanged.

Last round is all positive-quantity, non-DRAFT, non-CANCELLED items with the
latest valid item-level submittedAt timestamp in the current order. READY and
SERVED items qualify. Missing timestamps never invent a round. Cancelled rows
are excluded, and current remaining quantities are used after partial voids.
Transferred rows follow their existing timestamps in the receiving order.
This is current-order memory, not a persistent history across closed orders.

Recent selections aggregate by menuItemId and the existing
`sameModifierSelection` comparison. Ranking: latest submission first, then
aggregate quantity descending, then item ID and sorted option IDs for ties.
Thus latest-round selections naturally lead table history. Favorites follow,
deduplicated against table selections. No global popularity is fabricated.

Repeat calls the SAME `addItemWithModifiers` handler once per requested unit.
That handler calls P0.4 `draft.add` and the existing quantity handler, which
uses `changePending` or the existing scheduled PATCH queue. It reads the live
draft for matching, so rapid repeated inputs do not depend on a stale render.
Submit still flushes the same queue, without changes to its business logic.

Every repeat row is checked against the current merged availability overlay,
recipe configuration and active modifier options/group selection limits.
Unknown/unavailable items are omitted from chips and skipped on repeat.
Current prepared prices and modifier deltas feed the P0.4 local preview;
server responses still reconcile authoritative prices and reject stale intent.
No stock quantity or historical price is treated as pricing authority.

Deleted modifier references and rows with free-text notes cannot safely be
reconstructed through the existing add input. They are omitted from chips;
repeat skips and names them, with a short instruction to check availability,
modifiers, note or quantity. Other rows repeat immediately. The per-line
50-unit limit is retained; excess is reported, not silently counted as added.
Feedback counts locally accepted units, not server-confirmed items. Existing
P0.4 background errors still report subsequent server rejections.

Favorites count explicit accepted add inputs, including chips and repeats,
and preserve modifier selections. Counts rank first, latest action breaks ties.
The store belongs only to PreparedShell, keyed by restaurant/location/employee,
and clears on shell unmount (including existing logout/quick-lock navigation).
It survives table-route navigation, uses no disk storage, and has no DB table.
Another table can show the waiter's favorites (starred), but never inherits
another table's history or repeat-round button.

## Performance and tap count

Mounted React/jsdom scenario with delayed server response: repeat five units
was visible in 20.73 ms; quick-chip +1 in 4.40 ms in the final run. These measure committed DOM,
not hardware paint. Android tablet / Windows touch POS targets remain manual
QA: quick +1 <50 ms; entire repeat <100 ms.

For 2 Pivo + 2 Rakija + 1 Kisela, already in the active category and visible:

| Flow | Open table | Add units | Submit | Total |
| --- | ---: | ---: | ---: | ---: |
| P0.4 | 1 | 5 menu taps | 1 | 7 |
| P0.5 | 1 | 1 repeat tap | 1 | 3 |

Four fewer taps (57%); category changes/search could add more to the baseline.
The existing “Dodaj još” scroll/focus shortcut is optional and not counted.
Scrolling is not counted as a tap. The repeat button sits before menu search;
the sent-history area retains its existing bounded layout.
