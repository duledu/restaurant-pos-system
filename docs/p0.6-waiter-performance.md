# P0.6 waiter performance

## Scope and measurement

Baseline: `7496000cbe85f38d596c5d0ed65f40deb45e19e5`.
The benchmark runs the actual waiter shell, OrderClient, PosClient, active-order
projection, and mutation queue in local headless Chrome. It uses the production
React profiling build and existing production CSS, a 412×915 mobile viewport,
4× CPU slowdown, 240 menu items in 12 categories, 24 tables, and 80 submitted
rows per occupied order. Each API fixture responds after 200 ms. Three fresh
sessions are measured per version. No real database, account, or server is used.

`scripts/performance/waiter-benchmark.mjs baseline` reads the baseline source
directly from Git without checkout. `after` builds the current source. Run with
Node from the repository root, after a production build; Chrome must already
be installed. Raw results and isolated browser profiles stay in ignored
`.tmp/waiter-performance/`. No benchmark module is imported by the application.

Timing starts at the captured click/input event (before its React handler),
or immediately before a synthetic route swap. React Profiler measures render
work separately from event-to-commit. Two animation frames approximate the
next paint opportunity; this is **not** a measured pixel presentation time.
Cold open waits until the usable active-order panel exists. API timings include
the artificial transport delay and fixture execution, not a real backend.

Limitations: CPU throttling does not reproduce Android hardware or memory
pressure. Navigation swaps the real route components inside their persistent
shell, bypassing Next's router/RSC/chunk transport. Auth/logo controls are
stubbed; external font requests are disabled for repeatability. Consequently
these results do not certify online route, font, Wi-Fi, database, or Android
paint performance. Those remain explicit real-device benchmark tasks.

## Findings and changes

1. A cold order has a real sequential dependency: POST resolves/creates the
   current active order, then GET loads its items. POST returns a bare order.
   The fixture models at least 400 ms of transport here. Cached reopening
   already renders the table-owned snapshot immediately, while the same
   authoritative discovery runs in the background. Its loading flag now
   starts false when that snapshot exists, avoiding a redundant completion
   update. No placeholder order or second cache is created.
2. Every unchanged order/table/availability poll replaced objects and caused
   render work. Accepted JSON responses now structurally share unchanged
   fields and rows; identical order reads do not emit store notifications.
   Comparison happens **after** the existing ordering, pending-operation,
   Submit-revision and status-hold gates. All server fields are compared,
   including READY, prices, added fields and removed fields.
3. Cart updates rebuilt the menu and unrelated order rows. Memoized menu,
   category, submitted/history and draft-row boundaries now skip unchanged
   props. Stable event callbacks read the latest committed closure, preserving
   current table, draft, availability and Submit guards. Draft mutations keep
   their existing immediate local update, queue, debounce and retry paths.
4. Quick suggestions previously validated every historical candidate although
   only eight were displayed. They now stop at eight valid unique selections,
   preserving existing ranking. Menu ID lookup is indexed once per merged menu.

The menu filter and activeOrderView were already memoized. No additional
search index, virtualized list, second state store, or subscription framework
was justified by this fixture. New menu results still require DOM/layout work;
large broad searches remain a real-device hotspot.

## Preparation, network and prefetch audit

Preparation resolves identity first, then fetches snapshot, availability,
shift and tables concurrently. The snapshot already carries categories,
prices and modifier definitions. The first complete authoritative availability
overlay remains mandatory. Normal navigation does not fetch that menu again.

No operational API was removed: the audit found no safely redundant request
in the normal mutation path. Adds use their returned row, quantity changes
are debounced, and removes do not routinely GET the whole order. Error recovery
GETs are retained. Availability refreshes share an in-flight request.

For tables → A → three distinct adds → tables → B → A, operational requests
are three open POST/detail GET pairs plus three item POSTs: **9 before / 9
after**, plus cadence-dependent background polls. The fixture also records
every request in this sequence, including any polls. The five preparation
requests precede it and are not repeated. Next route/RSC requests are excluded
from this count and must be captured online.

No speculative order prefetch was added. Table summaries expose owner and
READY information, but no active-order ID. Calling openOrder speculatively
could create orders. Fetching all occupied orders would also multiply payloads
and require a new authorization-safe discovery contract. A future bounded
read-only active-order prefetch endpoint should be evaluated against measured
online cold-open latency, with the same table-owned controller/read guards.

## Polling and Submit

Cadences are unchanged: mounted order 4 seconds, shell tables/READY 5 seconds,
availability 15 seconds while the mounted order is open. Identical snapshots
now avoid visible work; real changes still propagate. Transport/payload counts
and battery/network cost are not claimed to improve. Server freshness still
waits for unresolved mutations to settle and for a later successful poll.

SSE already exists elsewhere in the backend, but a waiter event/delta protocol
is deferred. It needs reconnect, missed-event recovery and reconciliation
design, not merely replacing an interval. Measure event lag and network/battery
cost on real devices before that phase.

Submit still flushes the existing mutation queue, commits through the existing
transaction, then follows the existing event and PrintJob dispatch lifecycle.
Post-commit work is sequential today; it was not reordered without evidence
that the dispatch contract and delivery guarantees permit it. Payment, audit,
KDS, printing, inventory, auth and schema are unchanged.

## Mobile audit and real-device benchmark

The menu is text-based with no product-image decode cost. Category filtering
bounds its usual DOM; broad search can expose all 240 fixture items. Sent
history and the bottom panel both render their existing views of submitted
rows, so very large orders still have a sizeable DOM. Scroll containers and
thumb targets are preserved. No animations, artificial loaders, delays or
progress percentages were added. Existing shadows, transforms, backdrop blur
and READY pulse need compositor/scroll inspection on target Android hardware.
The global Inter stylesheet uses `display=swap`; online font loading/layout
shift remains outside this isolated fixture and was not changed globally.

On a real 4–6 GB Android phone/tablet, connect Chrome remote debugging and
record Performance plus Network with Preserve log. Record device/Chrome
version, viewport, Wi-Fi RTT, cold/warm route state and at least 20 samples per
action. Inspect Event Timing/paint, React profiling if a profiling build is
available, RSC/chunk requests, API duration, long tasks, layout shifts and scroll
frames separately. Repeat with weak Wi-Fi and three independent waiter sessions.
Exercise cold occupied/free open, cached reopen, A→B→A, add, rapid +1, decrement,
remove, category/search, modifiers, quick add/repeat, READY, failed add/retry and
Submit. Confirm submitted rows remain visible and only drafts are editable.
Targets remain local add/+1/category under 50 ms preferred, add under 100 ms,
cached reopen under 100 ms; cold authoritative discovery is reported separately.

No migration, environment edit, database connection or destructive test is
required by this pass. Nothing is pushed automatically.

Quiet 5.5-second interval: median React work 54.5 → 2.8 ms; commits 3 → 2. The optimized samples contain 0–2 commits, not a promise of zero background activity.

READY fixture change → detected rendered status: 731.8 → 464.0 ms, with 16.6 → 10.1 ms React work in that interval. Detection depends on where the fixture change lands in the unchanged polling cycle; the difference is **not** a realtime transport improvement. Worst-case polling lag remains roughly the cadence plus network/processing, and longer during unresolved mutations or outages.

The final request trace contains nine operational calls in each sample before and after, plus 0–1 baseline / 1 optimized table-summary polls. No menu/category/modifier/availability fetch is caused by these route changes. A request may overlap the next local add; that is intentional local-first behavior.

The second baseline recording used corrected capture-event start times rather than including DOM selector lookup time; the first sample overlapped the short unit-test run, while the other samples and optimized run had no validation process running. Browser/OS scheduling remains uncontrolled. Use the medians as directional evidence and use the real-device procedure above for acceptance.

Validation: **442 unit tests / 49 files pass**, including **115 waiter/READY tests / 7 files**. Four new regressions cover identical accepted references, selective sharing, added/removed server fields and READY delivery. All previous P0.3/P0.4/P0.5, active-order, race, retry and Submit tests remain green. No database integration suite was run.

Typecheck, production build and diff check pass. The build retains the existing
availability-effect `order` dependency warning. The order route is 9.57 kB
(previous build: 9.19 kB), with reported first-load JS 126 kB (previous 125 kB).
This is a render-work optimization with a small bundle cost, not a bundle-size
reduction. Submit and all server business logic remain unchanged.
