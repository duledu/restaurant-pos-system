# P0.6.1 waiter hot paths

Baseline commit: `717d59d9b8d5dfad54468ef4c4cbe543a68e95db`.

## Cold-open contract

Previously, table navigation called POST `/api/pos/orders`, which performed
table/shift validation and active-order discovery (or created an order for an
empty table). Its response contained bare order metadata. Only after receiving
the ID could the client GET `/api/pos/orders/:id` for rows and modifiers. The
second HTTP round trip was unavoidable under that response contract. Cached
order contents were already immediately usable; this primarily hurt cold opens.

Inspection now calls GET `/api/pos/orders?tableId=…` once. The authenticated
handler validates the table ID and returns the current active order with the
same item/modifier detail shape, or a genuine null order. It validates operator,
restaurant, active table, location, active shift and draft ownership. The order
query excludes completed/cancelled orders. The response is private/no-store.
This is one HTTP request, not a claim of one SQL statement: table and shift
validation and Prisma relation reads remain server work.

The client checks the response table identity, order table/location identity,
and complete item-array shape before passing it to the existing read guards.
No order ID is trusted from table summaries. Table summary payloads are
unchanged; no full orders are added to the 5-second table-grid payload.

An empty table now requires the explicit **Započni porudžbinu** action before
the existing open-order transaction runs. Inspection, navigation and polling
never POST an order. The command shares the existing table-owned queue and
status-read hold; rapid clicks/navigation cannot start a second command in
that shell. The existing server creation, shift and audit logic is unchanged.
This intentionally adds a start action for empty tables, rather than treating
viewing a table as authorization to create an order. Item additions still use
the original optimistic path after a real order exists.

The same order snapshot records whether an authoritative inspection has
completed, including a null result. This distinguishes unknown from known
empty without a second cache. Cached empty tables render locally and revalidate
in the background. Mounted empty tables also inspect read-only on the existing
4-second order cadence, so a remotely opened order does not remain invisible.
Null responses cannot erase newer mutations: all existing revision, ordering,
pending and status-hold checks still run before acceptance.

Inspection starts asynchronously in a layout effect, before the prepared menu's
paint, without awaiting a response on the render path. Loading completion is
queued before the external-store notification, avoiding a redundant completion
render. Menu DOM/component identity is preserved through hydration.

## Browsing/modifiers and routing

Category and search state now belong to a memoized MenuBrowser component.
Previously those changes rerendered TableOrderClient and reconstructed its
unrelated order/history element lists, even though individual rows were memoized.
The menu still uses the existing full-menu filter, original ranking,
current prepared prices, and authoritative availability overlay. Because DOM
creation dominated broad search, it displays the first 60 matches with a
thumb-sized **Prikaži još · 60 od N** action that adds the next 60 locally.
All matches remain reachable, precise queries still search the entire menu,
and categories are not capped. Changing the query resets the visible limit.
No result is silently discarded; no network request or artificial delay is added.

Modifier definitions were already memoized inside the modal. Keeping menu
browsing separate lets parent modifier/cart updates skip it, while category and
search changes skip the parent. Confirmation still calls the same local draft
controller with the selected option IDs; validation and price calculation have
not changed. Stable callbacks continue using the latest committed state.

Code review found that the table page only unwraps params and renders OrderClient;
the tables page renders PosClient, and their shared layout retains WaiterShell.
No duplicate route-level menu/order fetch was found. The existing keyed table
component remount is retained for isolation. No router rewrite or route-prefetch
strategy was added. Actual Next router/RSC latency was **not measured**: no
existing authenticated CDP browser was available. The fixture swaps these real
components inside the shell, so its route timing excludes RSC/chunk transport.

## Measurement method

Run `node scripts/performance/waiter-benchmark.mjs baseline` and `after` from
the repository root after a production build. The baseline is loaded from Git
without checkout; the optimized version uses current source. Results/profiles
are ignored under `.tmp/waiter-hot-path/`. No database is contacted. Chrome
must already be installed; the tool installs nothing.

Same fixture: production React profiling build, production CSS, 412×915 viewport,
4× CPU slowdown, 240 items/12 categories, 24 tables and 80 submitted rows per
occupied order, with a synthetic 200ms delay per API. The POST fixture returns
bare metadata as the real legacy endpoint does. Three fresh sessions per
variant. Validation processes are not run alongside final timing samples.

Cold open records the **first commit containing the usable order panel**, not
a subsequent loading-flag commit. Local interactions record their first commit,
not a later background server confirmation. Quantity assertions verify visible
add/decrement/repeat results. Rapid +1 uses separate events with intervening
frames; the reported time is for one tap within that sequence. Request start/end
times and React work are recorded separately. Two frames are only a paint
opportunity estimate, not pixel presentation measurement. Thus these fresh
paired values should not be subtracted directly from the earlier P0.6 report's
last-commit timings.

This remains a synthetic desktop benchmark, not Android certification or real
backend/network measurement. CPU slowdown and a viewport do not model RAM,
Wi-Fi, font transport or Android compositor behavior. Three samples are noisy;
the reported device target must be checked with real-device traces before any
latency SLA is claimed.

## Safety and verification

The activeOrderView projection, submitted read-only rows, pending queue,
clientMutationId, Submit revisions, reconciliation ordering, status holds,
table isolation and retry/idempotency paths remain intact. Payment, KDS,
printing, inventory and Submit business logic were not redesigned.

New tests cover occupied single-request inspection, no writes for empty
inspection, cross-table response rejection, location/shift/draft-ownership
authorization, late-null versus pending mutations, empty-table polling,
cached empty reopen, serialized explicit creation across navigation, category
selection through hydration/cart edits, search clearing and modifier selection.
Domain tests use a database mock with no write methods; no integration database
or destructive test was used. No migration or environment change is required.

The preferred cold target of 250 ms is not met by the median. The final
fixture samples are 326.5, 263.9, 273.2 ms, all below 350 ms. Earlier exploratory
samples exceeded 350 ms; these three final samples do not establish a maximum
on real devices. The matched results include slower quick-add, modifier-open
and B→A samples rather than hiding them. Add/+1/decrement improved, repeat and
cached reopen stayed within a few milliseconds, and all local mutation medians
remain below 15 ms. No claim of statistical non-regression is made from n=3.

Quiet 5.5-second interval: median React work 4.0 → 0.0 ms; commits 2 → 0.

Before, the active order ID becomes available between the first response and
the second request; submitted rows arrive only with the second response. After,
identity and rows arrive together and enter the same table-owned snapshot. The
remaining interval includes response parsing, React work, effects and scheduling.
Actual backend and Next latency remain unmeasured; server DB calls are not
simulated individually by the fixed 200 ms response delay.

Tables → A → three adds → tables → B → A now records **6 operational requests
versus 9 before**, plus cadence-dependent polls: three read-only inspections
and three item POSTs, replacing three discovery POST/detail GET pairs. No new
menu or modifier request is introduced.

Validation: **456 unit tests across 50 files pass**. This includes **129 tests
across 8 waiter/READY/inspection files**, with 14 targeted additions. Existing
P0.3/P0.4/P0.5, active-order restore, race, retry and Submit coverage remains
green. Domain tests are mocked; no live/destructive database tests were run.

Typecheck, production build and diff check pass. The order route is 9.98 kB
versus 9.57 kB at P0.6; reported first-load JS remains 126 kB. No migration,
environment modification, database operation or push is part of this checkpoint.
