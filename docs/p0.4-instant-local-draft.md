## Add idempotency audit and implementation

`OrderClient → POST /api/pos/orders/[id]/items → addOrderItemSchema →
orders.addItem → transaction(OrderItem + modifiers + OrderEvent) → { item }`.
Previously each successful POST created another row. The cart lock serialized
requests but could not protect a retry after a lost response. Submit keys do
not apply to adds.

The optional `clientMutationId` now becomes the existing append-only
OrderEvent primary key. The same transaction records an immutable normalized
add identity (menu item, original quantity, note, sorted modifier IDs) and
created item ID in the event payload. A replay checks order access first,
checks the receipt's order/type/input, and returns the current server item.
A concurrent event-PK conflict rolls back the losing transaction's item and
modifiers before reading the winner. Removed items retain their event receipt;
a later replay is rejected rather than recreating the item. UUID reuse for a
different order/input is rejected. Legacy clients can still omit the key.

No new table, column, migration, or payment/printing key is needed. Six guarded
PostgreSQL tests cover repeat and concurrent requests, payload mismatch,
removal, access control, and availability validation. The existing 16-test
multi-round suite also passes against the isolated TEST database.

## Local behavior

Before: tap → POST → response → cart row appears.

After: tap → local row appears in the same update → queued POST → server
price, modifiers, status and identity reconcile silently. The existing shell
owns a small table-scoped in-memory draft session and the existing mutation
queue. No global store, disk persistence or prediction was added.

Repeated identical selections increment one DRAFT row; different modifiers
stay separate. While create is in flight, +/- update desired quantity and
remove sets desired quantity to zero. The temporary identity remains usable
until the server create and any required PATCH/DELETE settle. A late response
never replaces a newer visible quantity. Different rows render immediately
even though their server requests remain serialized.

Navigating between waiter tables leaves sessions and requests alive. Submit
waits for the shared queue and refuses unresolved/failed additions. Its
existing guard and key also survive navigation. Polling and initial reads
cannot replace state spanning known mutations or Submit.

## Failure behavior

- Definite server rejection: remove only the temporary line and show a short
  Serbian message; retain the rest of the cart.
- Lost/network/server-error response: automatically retry once using the
  exact same mutation ID and immutable create payload.
- Continued uncertainty: retain the unresolved intent and show
  `Pokušaj ponovo`; Submit remains blocked. It would be unsafe to pretend
  rollback succeeded when the server may already have committed.
- A locally removed but uncertain add remains retryable in the session; once
  its server identity is recovered, DELETE finishes the removal.
- A lost DELETE response uses an order GET only on the failure path to verify
  absence. Normal adds never perform a full-order GET afterward.

local cart with the server response held unresolved. This is not a browser
paint or recommended-hardware benchmark; verify the <50 ms target on devices.

PostgreSQL integration tests. Typecheck, Prisma validation, and diff checks
